# P1 — fix before M1 sign-off

### P1-1 · Provider dialog throws away everything the user typed when validation fails
`onSave` closes unconditionally, before knowing whether the save was accepted:

```kotlin
// ProvidersScreen.kt:178-182
onSave = { name, baseUrl, apiKey, model, models ->
    viewModel.save(initial?.id, name, baseUrl, apiKey, model, models)
    adding = false; editing = null          // ← happens even on rejection
},
```
`save()` early-returns on blank name / bad URL and only sets `_message` ([ProvidersViewModel.kt:58-65](TeaTalk/app/src/main/java/com/teatalk/xs/ui/providers/ProvidersViewModel.kt#L58-L65)), so the user gets *dialog closed + snackbar "Name is required" + empty form*. This is the worst kind of error handling for a settings screen — a 4-field form is not cheap to retype.

**Fix (Compose-level):**
```kotlin
// ViewModel: return a result instead of a side-channel message
data class SaveResult(val ok: Boolean, val nameError: Int? = null, val urlError: Int? = null)
fun save(...): SaveResult   // no _message on validation failure

// Dialog: keep it open, show field-level errors
onSave = {
    val r = viewModel.save(...)
    if (r.ok) { adding = false; editing = null }
    else { nameError = r.nameError; urlError = r.urlError }
}
OutlinedTextField(..., isError = urlError != null,
    supportingText = { urlError?.let { Text(stringResource(it)) } },
    keyboardOptions = KeyboardOptions(keyboardType = KeyboardType.Uri, imeAction = ImeAction.Next))
```

### P1-2 · "Test" / "Fetch models" have no loading state inside the dialog — the only spinner is *behind the scrim*
[ProvidersScreen.kt:99-102](TeaTalk/app/src/main/java/com/teatalk/xs/ui/providers/ProvidersScreen.kt#L99-L102) puts `CircularProgressIndicator` in the screen's top bar, which is covered by the dialog's scrim ([ProvidersScreen.kt:326-341](TeaTalk/app/src/main/java/com/teatalk/xs/ui/providers/ProvidersScreen.kt#L326-L341) has no busy handling). On a 3–8s network call the dialog looks frozen → users double-tap → duplicate requests. `_busy` is also shared between test, fetch and save, so any of them toggles the same hidden spinner.

```kotlin
var testing by remember { mutableStateOf(false) }
var fetching by remember { mutableStateOf(false) }
TextButton(enabled = !testing && !fetching, onClick = {
    note = null; testing = true
    onTest(baseUrl, keyForCall()) { note = it.resolve(context); testing = false }
}) {
    if (testing) CircularProgressIndicator(Modifier.size(14.dp), strokeWidth = 2.dp)
    else Text(stringResource(R.string.providers_test))
}
```
Also: failure text is painted in `primary` brown ([ProvidersScreen.kt:342-344](TeaTalk/app/src/main/java/com/teatalk/xs/ui/providers/ProvidersScreen.kt#L342-L344)) — "Failed: …" currently reads as success. Split `note` into `note: TestNote?(text, isError)` and tint with `error` + a leading icon.

### P1-3 · Chat auto-scroll hijacks the list on every token (and is off by one item)
```kotlin
// ChatScreen.kt:197-200
LaunchedEffect(messages.size, streamText.length, streaming) {
    val count = messages.size + if (streaming) 1 else 0
    if (count > 0) listState.scrollToItem(count - 1)
}
```
Two defects: (a) the date header is `item {}` at index 0 ([ChatScreen.kt:219-229](TeaTalk/app/src/main/java/com/teatalk/xs/ui/chat/ChatScreen.kt#L219-L229)), so `count - 1` lands one item early — the newest message (or the streaming bubble) can stay just below the fold; (b) because the key includes `streamText.length`, **every token re-scrolls instantly**, so a user who scrolls up mid-reply is yanked to the bottom continuously. This is the single most user-visible streaming bug.

```kotlin
val atBottom by remember {
    derivedStateOf {
        val info = listState.layoutInfo
        val last = info.visibleItemsInfo.lastOrNull()?.index ?: 0
        last >= info.totalItemsCount - 2
    }
}
LaunchedEffect(streamText.length, messages.size) {
    if (atBottom) listState.scrollToItem(listState.layoutInfo.totalItemsCount - 1)
}
```
And add the "new message ↓" pill when `!atBottom` (QQ/WeChat both have it).

# TeaTalk M1 Security Review — Network / Credentials / Logging

**Scope:** `app/src/main/java/com/teatalk/xs/{data,log}/`, `core/…/log/`, `AndroidManifest.xml`, `res/xml/`, `app/build.gradle.kts`, plus the UI call sites that touch secrets (`ProvidersViewModel.kt`, `ProvidersScreen.kt`, `AboutScreen.kt`, `ChatScreen.kt`).
**Method:** full-file read of every in-scope source, taint-trace of the API key from `SecretStore.put` → disk → `active()` → `Authorization` header, audit of every `TeaTalkLog.*` call for secret-bearing fields, docs-vs-code guarantee diff, and bytecode verification of OkHttp 4.12.0's redirect handler (constant-pool inspection of `okhttp3/internal/http/RetryAndFollowUpInterceptor.class`).
**Baseline:** git `85d7507`, v0.3.1. Working tree left unmodified.

Four Medium issues remain; all are "one refactor away from a leak" rather than live exfiltration.

## R-01 — API key tail logged, and the full key when it is ≤4 characters (Medium)

`TeaTalk/app/src/main/java/com/teatalk/xs/data/model/SecretStore.kt:26-29`

```kotlin
fun put(providerId: String, apiKey: String) {
    prefs.edit().putString(keyName(providerId), apiKey).apply()
    TeaTalkLog.i("Net", "secret.put", "provider" to providerId, "tail" to apiKey.takeLast(4))  // :28
}
```

**Why it's a defect, not just noise:** the encrypted-at-rest control is correct, and then the secret is written in cleartext to the *unencrypted* sinks — logcat, `filesDir/logs/teatalk-yyyyMMdd.log`, the 2000-entry `RingBufferSink`, and therefore the diagnostics export the user is asked to share in bug reports. `takeLast(4)` is a **variable-length** disclosure: for `sk-local`, `none`, `test`, or the 6-char keys people use against LM Studio / Ollama (`docs/06-模型配置设计.md:26` explicitly targets 局域网 endpoints), `takeLast(4)` of a 4-char key returns the *entire key*.

**Exploit scenario:** user configures a local gateway with key `abcd` (or a self-signed proxy with an 8-char secret). Every save writes `secret.put provider=<uuid> tail=abcd` to logcat. The user files an issue with a diagnostics export (the About screen *invites* this: `AboutScreen.kt:125-130`). The tail becomes part of a public artifact, and for short keys it is the credential. Secondary: any sibling process on a debuggable build (`adb logcat`, `docs/07-日志设计.md:90` recommends exactly that grep) sees it.

**Note the guarantee gap:** `docs/06:99` and `docs/07:62` define the acceptance test as "`adb logcat | grep -i "sk-"` 与导出日志全文搜索 key 均为 0 命中". That test **passes while this bug ships**, because a 4-char tail contains no `sk-` prefix. The acceptance criterion is written against the wrong property.

**Fix — delete the field:** if you need "was a key stored", log existence, not material:

```kotlin
TeaTalkLog.i("Net", "secret.put", "provider" to providerId,
             "fp" to Redact.fingerprint(apiKey), "len" to apiKey.length)   // hash=1a2b3c4d,len=51
```

Masking for *UI* stays in `SecretStore.masked()` (`:40-42`), but make it refuse to echo short secrets:

```kotlin
fun masked(providerId: String): String? =
    get(providerId)?.let { if (it.length < 12) "****" else "****" + it.takeLast(4) }
```

**Regression test (add to `core` or `app`):** assert that after `SecretStore.put("p", key)` the ring buffer contains **no** substring of *any* 4-char window of `key` — that property, unlike the `sk-` grep, actually fails on regression.

## R-02 — Diagnostics export is a credential-adjacent intelligence package (Medium)

`TeaTalk/app/src/main/java/com/teatalk/xs/log/Diagnostics.kt:39-53`, `TeaTalk/app/src/main/res/xml/file_paths.xml:3`

```kotlin
fun exportToFile(context: Context, ring: RingBufferSink): File {
    val file = File(context.cacheDir, "teatalk-diagnostics-${System.currentTimeMillis()}.txt")  // :40
    file.writeText(header(context) + "\n" + recentLines(ring, limit = 2000)…, Charsets.UTF_8)  // :41
    return file                                                                                // never deleted
}
fun shareIntent(context: Context, file: File): Intent {
    val uri = FileProvider.getUriForFile(context, "${context.packageName}.files", file)        // :46
    … addFlags(Intent.FLAG_GRANT_READ_URI_PERMISSION)                                          // :51
}
```

Three compounding issues:

1. **Content:** header (`:28-36`) = app version, package, `Build.MANUFACTURER`/`MODEL`, Android release+API, DB version, timestamp — a fingerprintable device identity. Body = up to 2000 log lines including every `provider.save` with `host=`, every `chat.req.start` with the endpoint path, and R-01's `tail=`. Together that is "which private gateway this user talks to, with which model, and 4 chars of the key" — i.e. a targeted-phishing and key-completion starter kit if it lands in a public issue thread.
2. **Scope:** `file_paths.xml:3` grants `<cache-path name="diagnostics" path="." />` — the FileProvider root is **all of `cacheDir`**, not just diagnostics. `getUriForFile` can only produce URIs you ask for, so this is not exploitable today, but it removes the guardrail: any future "share this" call silently gets authority over Coil's image cache and anything else in cache.
3. **Hygiene:** the export is never deleted, so keys-tails/hosts accumulate in `cacheDir` indefinitely (cache is only reclaimed under storage pressure).

**Fix:**

## R-03 — The shipped artifact is a debuggable build (Medium)

`TeaTalk/app/build.gradle.kts:21-36`

## R-04 — Cleartext policy is implicit; the documented switch was never built (Medium)

| Stated guarantee | Implementation |
|---|---|
| `docs/06:11` "API Key … 不进备份" / `:103` "明文 http：默认禁止… 允许用户在「高级」里打开… 展示风险提示… 默认校验 `https://`，白名单 `127.0.0.1`/`localhost`/`10.*`/`192.168.*`" | No `networkSecurityConfig`, no `usesCleartextTraffic`, no advanced toggle, no host allowlist, no risk dialog anywhere (`grep` for all of them: 0 hits) |

Code path:
- `ProvidersViewModel.kt:62-65` accepts `http://` and `https://` with equal standing; nothing warns.
- `ProviderRepository.kt:45` persists `baseUrl.trim().trimEnd('/')` — **no scheme/host validation in the data layer**, so a legacy/tampered row (rooted device, `adb` on a debug build, restored backup) reaches `ChatClient.kt:79` `baseUrl.trimEnd('/') + "/chat/completions"` unvalidated.
- `ChatClient.kt:92-96` then puts `Authorization: Bearer $apiKey` on that URL.

**Why it isn't High today:** `targetSdk = 34` and `android:usesCleartextTraffic` absent ⇒ `NetworkSecurityPolicy` denies cleartext by default, and OkHttp 4.12 consults it via `AndroidPlatform.isCleartextTrafficPermitted`, so an `http://` provider fails closed — the key is never transmitted in the clear **on Android**. The risk is (a) a functional trap: LAN §7 users get an opaque `CLEARTEXT … not permitted` failure with no explanation and the UI calls it "接口地址需要以 http:// 或 https:// 开头" (`strings.xml:204`), and (b) one added manifest attribute or a `network_security_config` with `cleartextTrafficPermitted="true"` flips this to High instantly, with no code guard in between.

**Exploit scenario (post-flip):** on hostile Wi-Fi, `http://192.168.1.20:1234` + `Bearer sk-…` is sniffable by any device on the LAN in plaintext.

**Fix — make the policy explicit and enforce it in the data layer:**

```xml
<!-- res/xml/network_security_config.xml, referenced from <application android:networkSecurityConfig=…> -->
<network-security-config>
    <base-config cleartextTrafficPermitted="false">
        <trust-anchors><certificates src="system" /></trust-anchors>
    </base-config>
</network-security-config>
```
```kotlin
// ProviderRepository.save()
val parsed = HttpUrl.parse(baseUrl.trim().trimEnd('/'))
    ?: return SaveResult.Invalid("接口地址格式不正确")
if (parsed.scheme != "https" && !(allowCleartext && parsed.host.isPrivateLan())) {
    return SaveResult.Invalid("仅支持 https；局域网明文需在高级设置中显式开启")
}
```
and re-validate at the sink (`ChatClient.stream`) so stored rows are never trusted. Ship the `允许明文连接（仅本机/局域网）` switch promised in `docs/06:103` **before** anyone relaxes the NSC — that ordering is the whole control.

## R-05 — Bearer token and redirects (Low)

`ChatClient.kt:66-70` builds the client with no redirect policy, so `followRedirects = true`, `followSslRedirects = true` (defaults).

Verified against the actual artifact (`okhttp-4.12.0.jar`, `RetryAndFollowUpInterceptor.buildRedirectRequest`): the constant pool contains `Authorization` alongside `removeHeader`, i.e. **4.12 already strips the `Authorization` header on cross-host redirects**. So the classic "attacker-controlled endpoint 302s the key to `evil.com`" attack is **not** present. Residual: a *same-host* redirect (`https://api.host/v1/chat/completions` → `https://api.host/collect/...`, e.g. after a CDN/gateway compromise or an endpoint typo) keeps the header; and a **custom `baseUrl` is user-supplied**, so redirects toward an attacker-adjacent path on the same origin are reachable.

**Fix (cheap, strict):** `.followRedirects(false)` on the client used for key-bearing calls, and treat 3xx as `ChatError.BAD_RESPONSE` with a "接口地址被重定向，请检查 Base URL" message. Also `.followSslRedirects(false)` so an `https→http` hop can never silently become cleartext on a platform that allows it.

## R-10 — Redaction is the caller's job, by design (Low)

`TeaTalkLog.kt:72-73` (`safeFields[k] = value?.toString() ?: "null"`) performs **no** filtering; `Redact` is a library call sites may forget. ## R-13 — Keystore work on the main thread (Low)

`SecretStore.masked()` (`:40-42`) decrypts via `prefs.getString`, which on first call constructs `MasterKey` + `EncryptedSharedPreferences` (Keystore + `KeyStore` I/O). ## R-14 — Card import surface (Info)

`AndroidManifest.xml:16-44` exports `MainActivity` with `VIEW`/`SEND` filters for `image/png`, `application/json`, `application/octet-stream (and) application/zip` — any installed app can push a card in silently (`MainActivity.kt` `handleExternalCard` → `CharacterRepository.importCard`). ## Architecture verdict

**B+ — a well-built M1 that is 2 refactors short of a clean M2.**

What's genuinely good, and better than typical M1 code: `:core` is *honestly* pure (no Android, no coroutines, no OkHttp), the log layer is production-grade (sink isolation via `runCatching` + dropped counter, URL/key redaction, single-writer file sink with rotation), error classification is a proper `sealed interface ChatError` with HTTP codes, the greeting insert already fixed a real count→insert race with `@Transaction` (`CharacterDao.kt:77-84`), and there are 44 green tests including 6 MockWebServer contract tests for 401/429/5xx/timeout/断流.

The structural problem is **one seam missing in exactly the place that matters**. UI → VM → Engine → Client is a straight line of concrete classes with no ports:

```
ChatEngine(CharacterRepository, ProviderRepository, ChatClient)   // ChatEngine.kt:22-26
```

`ProviderRepository` pulls `SecretStore` (EncryptedSharedPreferences) and `AppPrefs` (Android `Context`), so `ChatEngine` **cannot be constructed in a JVM unit test at all**. That is why there are 44 tests and zero of them touch the engine, the ViewModel, or the DB — i.e. zero coverage of the three places where this milestone's real risk lives (persistence-on-complete, cancellation, prompt assembly).

Secondary finding: the chat VM is not in `ChatViewModel.kt` — `ChatViewModel` + 5 composables live in one 451-line `ChatScreen.kt`.

For M2, two directions, and I'd take the cheap one now:

| Option | Shape | Cost | When it wins |
|---|---|---|---|
| **A (recommended)** | 3 narrow ports in `:app/data/port` (`ChatTransport`, `ProviderConfigSource`, `ChatHistorySource`) + a pure `buildPrompt()` in `:core` | ~4h | Unlocks every P1 regression test; fully reversible; no module churn |
| B | full hexagonal: `:domain` / `:data` / `:app`, everything behind ports | 2–3 days | Only if M3 brings multi-format protocols + a ST-parity engine ref, which is still speculative |

## P1 blockers

**P1-1 · `stop()` can persist the reply twice** — `ChatScreen.kt:129-141` vs `ChatEngine.kt:95-102`.
`job.cancel()` is cooperative. If the collector is already suspended inside `characters.addMessage(ROLE_ASSISTANT, reply)` (`ChatEngine.kt:98`, a Room insert that is *not* cancellable once dispatched), the full reply lands; then `stop()`'s `launch` inserts `partial` (`ChatScreen.kt:135`) — a prefix of the same text. The user sees two assistant bubbles. `stop()` also has no `if (!_streaming.value) return` guard, so a double-tap re-inserts the same partial (the second tap reads `_streamText.value` before the first `launch` clears it). *Fix:* make finalization single-owner — either `stop()` awaits cancellation (`cancelAndJoin`) and writes through one `ChatRepository.finishMessage()`, or (better, see P1-5) give `MessageEntity` a `status` column and *update* the row instead of inserting a second one. **3h**

**P1-2 · `send()` guard is racy** — `ChatScreen.kt:116-120` vs `:149`.
`_streaming` is set *inside* the launched coroutine, not in `send()`. Two taps in the same frame both pass `if (_streaming.value) return`; two streams start, `job` is overwritten (first stream becomes un-cancellable — the Stop button can't stop it), and two assistant rows are inserted in arrival order. *Fix:* set `_streaming.value = true` synchronously before `launch`, keep a `Set<Job>`, or `Mutex.withLock`. **1h**

**P1-3 · Mid-stream error frames are silently swallowed ⇒ truncated replies saved as success** — `ChatClient.kt:196` (`deltaOf` returns `null` → `continue` at `:141`).
Providers (Azure, OpenRouter, overloaded proxies) emit `data: {"error":{...}}` *after* deltas. `deltaOf` can't find `choices` → null → ignored → EOF → `Completed` at `:169` → `ChatEngine.kt:98` persists a truncated reply with no error. `finish_reason:"length"` is likewise invisible. This is the most user-visible correctness bug: users get silently cut-off roleplay with no retry affordance. *Fix:* in the loop, if the parsed JSON has an `error` object → `emit(Failed(NETWORK, msg.take(200)))` and abort; surface `finish_reason` as `ChatEvent.Completed(reason)` or a `TRUNCATED` failure. **2h**

**P1-4 · Navigating back mid-stream orphans the user message** — `HomeScreen.kt:176` (`viewModel(key = "chat-$id", …)`) is nav-entry scoped, so `popBackStack` → `viewModelScope` cancel → `call.cancel()` via `ChatClient.kt:100` → nothing persisted. User message stays in DB with no reply, no error banner, no retry hint. Also `ChatScreen.kt:159-162` clears `_streamText` in `finally`, so if the final insert fails the text just vanishes. *Fix (real fix is architectural):* generation must outlive the screen — an application-scoped `CoroutineScope` owned by `ChatEngine`/a `ChatRepository`, plus a `messages.status` of `streaming|done|stopped|failed` so a returning screen can show "generation interrupted — retry". **1d**

**P1-5 · Cold-flow side effects ⇒ `reply()` is not idempotent** — `ChatEngine.kt:28-38`.
`characters.addMessage(ROLE_USER, text)` runs *inside* the returned `Flow`. Any second collection (VM retry after a transient failure, a re-subscribe, or a test collecting twice) inserts the user message again. `retry()` only avoids it by duplicating the stream builder (`:40-43`). *Fix:* split into `suspend fun sendUserMessage()` (write) + a read-only `streamReply()`, or make the flow hot (`SharedFlow`) created once per send. **2h**

**P1-6 · `model = provider.model.ifBlank { card.name }`** — `ChatEngine.kt:75`.
Falls back to the *character name* as a model id → guaranteed HTTP 400/404 from every provider, surfaced as the generic "服务端返回错误（HTTP 404）". *Fix:* blank stays blank and fails fast with a new `ChatError.NO_MODEL` ("未选择模型"). **30m**

**P1-7 · `active()` conflates "no provider" with "key missing"** — `ProviderRepository.kt:84-87`.
Three distinct causes (`activeProviderId == null`, row deleted, `secrets.get()` null) all return `null` → `ChatError.NO_PROVIDER` → "还没有配置模型，去「我的 → 模型与接口」添加一个" even when the provider row exists and only the key was lost (e.g. EncryptedSharedPreferences restore failure, which is a *known* real-world failure after backup/restore). *Fix:* return a sealed `ProviderResolution` → `NO_PROVIDER | NO_KEY | OK`. **1h**

**P1-8 · Decrypted API key written to the persistent log** — `SecretStore.kt:28`: `"tail" to apiKey.takeLast(4)`.
Contradicts the project's own stated rule ("日志与 UI 都只出现尾部 4 位" is a UI rule, but the file sink keeps it 3 days) and makes the `docs/07` acceptance "grep sk- 0 命中" trivially true while still leaking 4 chars of a live secret per save. Replace with `Redact.fingerprint(apiKey)`, which is already tested and unused here. **15m**

## SSE parser: correctness and edge cases

Current shape: `Sse.dataOf` is a **per-line filter** (`Sse.kt`), consumed line-by-line at `ChatClient.kt:133-134`. It is not an event-block parser.

| Case | Verdict |
|---|---|
| Chunk splits (HTTP body boundary mid-line) | **Safe by construction.** `source.readUtf8Line()` never returns a partial line, and `0x0A` cannot occur inside a multi-byte UTF-8 sequence → no mojibake. This is the one place the implementation beats its tests (no test covers it). |
| `\r\n` line endings | Handled — `readUtf8Line` strips a trailing `\r`; then `trim()`. |
| Multi-line `data:` continuation (spec: concatenate with `\n`) | **Unsupported.** Each half fails `deltaOf` JSON parse → dropped by `getOrNull()` with no log ⇒ silent truncation. OpenAI-compatible servers send one line per event, so it works in practice, but a spec-compliant proxy (or a very long single delta folded by a middlebox) breaks. |
| `[DONE]` | Exact match after `trim()` → tolerant to `data: [DONE]` + trailing spaces/CR. But `event: done` framing is ignored (`dataOf` returns null for non-`data:` lines) — rare, acceptable if documented. |
| EOF without `[DONE]` | Tolerant: `chunks > 0` ⇒ `Completed` (`:169`), `chunks == 0` ⇒ `BAD_RESPONSE("no content")` (`:167-168`). Good design. |
| `data:` with no space / empty `data:` | Covered by `SseTest` for the space case; empty `data:` payload yields `""` which `isDone` rejects and `deltaOf` drops. OK. |
| Keepalive comments (`: ping`) | Ignored correctly. |
| JSON parse failures | Swallowed silently (`runCatching{…}.getOrNull()` at `:196`) — no `w` log ⇒ "why is my reply short" is undebuggable. Add `log.w("Net","sse.bad_frame", "len" to data.length)`. |
| Role deltas / `finish_reason` / `usage` | All ignored (`deltaOf` reads only `choices[0].delta.content`). No token accounting for M2 budgets. |

The refactor that pays for itself: an incremental **event-block** parser in `:core` (`SseParser.feed(chunk): List<Event>` — accumulator + blank-line dispatch + `data:` join), which is what makes multi-line and split-chunk tests meaningful instead of "Okio does it for us".

## Coroutines, threading, cancellation

- Blocking `call.execute()` + `readUtf8Line()` on `Dispatchers.IO` via `flowOn` (`ChatClient.kt:193`) — legitimate. Cancellation is wired twice: `invokeOnCompletion { call.cancel() }` (`:100`, registered before `execute`) and `finally { call.cancel() }` (`:190`). Works.
- Bug-adjacent: `catch (IOException)` (`:177`) logs `chat.req.fail kind=network` even when the IOException is the *cancellation*'s `Canceled`. Add `currentCoroutineContext().ensureActive()` at the top of the catch to demote it to the existing `chat.req.cancel` path — otherwise the exported log lies about cancellation.
- `invokeOnCompletion` handler is never disposed (harmless, job lifetime).
- `CharacterRepository` wraps almost every method in `withContext(Dispatchers.IO)` while Room's suspend DAOs are already main-safe (`:54,56,106,116,120,132,164,181,195,211`) — but `find` (`:51`) and the `observe*` flows are not wrapped. So the rule is neither applied nor needed; it just obscures where IO actually happens. Remove the wrappers.
- `ProvidersViewModel.save/testConnection/fetchModels` (`:66-81, 102-113, 125-134`) have **no `try/finally`** around `_busy`. Any throw (disk full, keystore failure, `JSONArray` OOM) leaves the spinner stuck forever and — since `viewModelScope` has no handler — crashes the app. `save` also has no error path at all.
- `testConnection(onResult: (UiText) -> Unit)` — callback escaping from a VM into a dialog's `remember` state (`ProvidersScreen.kt:328-330`) is a Compose anti-pattern; stale-callback risk plus it bypasses the message channel. Model it as state.

## State modeling

Six independent `StateFlow`s (`ChatScreen.kt:91-108`) + a bare `job` field is not a state model, it's five booleans that can disagree: `streaming=true` with `streamText=""` is "thinking", but so is a *failed* stream in the one frame before `finally` runs. M2 needs `Idle | Streaming(text, startedAt) | Stopping | Failed(cause, retryable)` anyway. Collapse into one `data class ChatUiState`.

`_error: UiText?` throws the `ChatError` away (`:156`), so: nothing can log/telemetry the cause, and **`retry()` is offered for `NO_PROVIDER`/`NO_MODEL`**, where it is guaranteed to fail identically. Keep `ChatError` in the state; `UiText.chatError()` mapping already exists and `err.resolve(context)` is already called at the render edge (`:245`) — it is a one-line move.

`UiText` is pragmatic, but two issues: (a) `ofPlural` (`UiText.kt:25`) is **dead code and broken** — `resolve()` calls `getString(res, …)` and never `getQuantityString`, so if anyone wires it up it will crash or print the raw quantity; (b) `ChatError` lives in `:app/data/net/ChatClient.kt:30-45`, so if the prompt engine moves to `:core` in M2 the error type must move with it. `ChatError`/`ChatEvent`/`PromptMessage` belong in `:core`; the `@StringRes` mapping belongs in `:app/ui`.

## Room schema & migration hygiene

- **`exportSchema = false`** (`TeaTalkDatabase.kt`) — no schema history, therefore `MigrationTestHelper` is impossible and the hand-written v3 DDL can drift silently from the entity. Turn it on with `room.schemaLocation`, commit the JSON, add `androidTest` (currently absent entirely). **3h, highest-value DB item.**
- v3 DDL vs entity: types and NOT NULL match by inspection, and `messages` already had `Index("characterId")` in v1 (verified: `git show 22058a4:…/Entities.kt`), so there is no Room index-validation crash. `MIGRATION_1_2` defaulting `updatedAt = 0` is benign because `observeAll` falls back to `createdAt DESC` on ties — worth a comment, since it depends on the ORDER BY.
- `CharacterRepository.delete` (`:106-107`) does `deleteMessages` + `delete` as two separate DAO calls: no `@Transaction`, no FK `ON DELETE CASCADE`, no avatar cleanup. Add `foreignKeys = [ForeignKey(CharacterEntity::id, "characterId", onDelete = CASCADE)]` + `@Transaction deleteWithMessages()`, and delete the avatar file in the same suspend function. **2h**
- `observeChats` (`CharacterDao.kt:94-104`) runs two correlated subqueries per row and `messages` has no `(characterId, createdAt)` composite index. Fine at this scale; one-line win: `Index("characterId", "createdAt")`.
- No `conversations` concept: `messages` is one flat stream per character and the provider/model are *global* (`AppPrefs.activeProviderId`). Per-chat multi-provider (an explicit M2 goal) therefore needs a schema decision **before** more rows accumulate — see below.

## DI & layer boundaries

`AppContainer` manual DI is the right size. Complaints, all small: side effects in `init{}` (installs sinks, sets `minLevel`, logs `app.start`) make construction non-idempotent; one dependency is resolved with a fully-qualified name (`com.teatalk.xs.data.net.ChatClient()`) while the rest are imported; and every collaborator is exposed as a concrete class, which is the P1-1-through-5 test blocker.

One leak worth calling out: `ProvidersScreen.kt:173` passes `storedApiKey = viewModel.apiKeyOf(it.id)` **decrypted** into the dialog, purely so `keyForCall` (`:278`) can re-test with a saved key. The plaintext key should never enter the composition tree; expose `testConnection(providerId: String?, baseUrl, enteredKey: String?)` and resolve the stored key inside the data layer. Also `ProvidersScreen.kt:168` renders `ProviderEditDialog` without `key(...)`, so `remember{}` field values survive switching from provider A to provider B (stale dialog). **1h**

## Error taxonomy

`NO_PROVIDER | UNAUTHORIZED | RATE_LIMITED | HTTP(code) | TIMEOUT | NETWORK | BAD_RESPONSE` (`ChatClient.kt:30-45`) is decent but misses the four cases that actually bite:

```
NO_KEY           // provider row exists, key lost        ← P1-7
NO_MODEL         // provider.defaultModel blank          ← P1-6
TRUNCATED        // finish_reason == "length"            ← P1-3
STREAM_INTERRUPTED // error frame mid-stream, deltas kept ← P1-3
```

Also `ChatEvent.Failed.detail` (body excerpt, `:124`) is dropped at `ChatScreen.kt:156` — either show it in a "详情" expander or log it once at the VM edge. And there is **no retry policy**: 429 with no `Retry-After` parsing, no backoff, no jitter — for M2 with 20-message prompts on rate-limited endpoints this will be the most common user-visible failure.

## M2 readiness — the three decisions to make before writing the prompt engine

1. **`PromptMessage` type, in `:core`.** `ChatClient.stream(messages: List<Pair<String,String>>)` (`ChatClient.kt:76`) is lossy: no `name`, no images, no tool calls, no role type. World-info entries need `role` + insertion slot anyway (`WorldInfoEntry.position/depth/role` are already modelled and tested but never injected — `WorldInfoEngine` is referenced only by its own test). Replace the pair with `data class PromptMessage(role, content, name: String? = null)` and a pure `buildPrompt(card, history, activatedEntries, budget): List<PromptMessage>` in `:core` — no coroutines, no Android, unit-testable against the 20 golden cases docs/00 already promises.
2. **`MessageEntity.status` + conversation-level provider/model.** `retry`, prompt budget, and per-chat multi-provider all assume one flat message stream with a *global* active provider. A `conversations(characterId PK, providerId, model, presetJson)` table plus `status IN (streaming, done, stopped, failed)` fixes P1-1 and P1-4 *structurally* (update the row instead of inserting a second) rather than with the current partial-insert hack. This is the cheapest moment to decide it — before more `messages` rows exist.
3. **Card fidelity gap.** `CardViewParser` already parses `mesExample` and `postHistoryInstructions`; `ChatEngine.systemPrompt` (`:113-131`) uses neither, concatenates up to 4×6000 chars with no token budget, and never injects world info. That's the concrete content of the "prompt engine" milestone: `mes_example` as few-shot, `post_history_instructions` at the tail, world info by `order`/`position`, and a tokenizer-based budget (`WorldInfoEngine`'s `content.length + 2` is a chars proxy).
