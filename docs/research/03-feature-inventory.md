# 03 · SillyTavern 功能盘点与 TeaTalk 取舍建议（MVP 边界）

> **作者**：researcher-ux（产品/UX 研究）
> **日期**：2026-10-23
> **对象**：SillyTavern v1.19.0（`D:\Project\TeaTalkApp\SillyTavern`）+ 官方文档（`D:\Project\TeaTalkApp\SillyTavern-Docs`，93 个 md / 817 KB）
> **性质**：**只读**调研。未修改 ST 目录任何文件。本文所有数字均可用附录 A 的命令复现。
> **服务对象**：TeaTalk（原生 Android）MVP 边界定义、首屏信息架构、交互重设计。

## 0. 一页纸结论（TL;DR）

| # | 结论 | 关键证据 |
|---|---|---|
| 1 | **ST 不是一个"聊天 App"，而是一个「LLM 前端工作台」+「角色卡运行环境」+「扩展宿主平台」三合一**。它的复杂度不是"功能多"，而是三种产品形态叠在同一个界面里。 | 单页 `index.html` 8231 行；201 个前端 JS 文件共 118,330 行；服务端 96 个文件 29,171 行 |
| 2 | **ST 必须跑一个 Node 服务端**。前端所有读写都走 `/api/*`，服务端有 **44 个 endpoint 路由文件**。官方 Android 方案是 Termux + git clone + `node` + `nano config.yaml`（159 行文档）。**"干掉服务端"是 TeaTalk 区别于所有 ST 套壳/网页版的最大价值点。** | `public/scripts/openai.js:3148` `const generate_url = '/api/backends/chat-completions/generate'`；`SillyTavern-Docs/Installation/Android.md` 全文 |
| 3 | **冗余是可量化的，且远超"功能列表"给人的印象**：9 个顶层抽屉、556 个 input、132 个 select、605 个 option、297 个斜杠命令、157 个宏、44 个扩展（官方文档口径）。**普通用户 80% 场景只触及其中约 6%**。 | 见 §3 冗余量化表 |
| 4 | **最该砍的不是"功能"，而是"三套并存的设置入口"**：AI 配置面板、User Settings 面板、Formatting 面板互相重叠，同一件事（如上下文长度）在 3 个地方能改。这是"功能冗余"体感的第一来源。 | §6 冗余四来源 |
| 5 | **移动端最该重设计的不是配色，是"hover 依赖"**。ST 大量交互建立在桌面 hover 上（每条消息 13 个图标悬停展开、tooltip、右键菜单）。手机上这些全部失效，ST 自己是"桌面缩小版"而非移动设计。**ST 官方明确禁用移动端快捷键，移动端手势只有 1 处（生成中滑动）**。 | `index.html:7412-7438`；`SillyTavern-Docs/Usage/Chatting/hotkeys.md`："Hotkeys are disabled for mobile devices." |
| 6 | **MVP 的天花板由"数据模型"决定，不由"功能数量"决定**。分支、正则、变量、群聊、媒体这些 V1 功能现在不做，但**字段必须现在就进库**，否则 V1 要做数据迁移。这是本文 §12 的核心。 | §12 预留架构位 |

**一句话定位建议**：TeaTalk = 「3 步开始的角色扮演聊天 App」。
对用户的承诺不是"功能更全"，而是 **"装完就能聊，不用先当运维"**。

## 1. 盘点方法与证据等级

### 1.1 证据来源

| 来源 | 用途 | 可靠性 |

### 1.2 "80% 场景"的方法论声明（重要）

本仓库没有用户埋点数据，因此本文所有 **"使用频率"标注为估计**，依据是三类间接信号：

1. **官方文档的"必需路径"与"可选路径"之分**：ST 官方 `Usage/quick-start.md` 只讲 4 件事（连 API、建角色、开始聊天、世界书），其余章节都是"进阶"。
2. **功能在 UI 上的默认可见性**：默认关闭 / 藏在 inline-drawer 里的功能，说明官方认为它不是多数人用的。
3. **移动端行为差异**：ST 自己为移动端禁用的功能（快捷键、hover 动作），说明它们在设计上就不被认为能在小屏成立。

> 结论中凡涉及"频率"的判断，请按 **方向可信、量级可信、精确值不可信** 来使用。

## 2. ST 的产品形态与架构事实

### 2.1 三种产品形态的叠加

| 形态 | 目标用户 | 在 UI 上的表现 | 对 TeaTalk 的含义 |
|---|---|---|---|
| **A. 聊天前端** | 所有用户 | 角色列表 → 对话 → 输入栏 | ✅ MVP 主体 |
| **B. 提示词工程台** | 进阶玩家 | Prompt Manager 树、instruct 模式、context 模板、采样器 20+ 参数、tokenizer、logprobs | ❌ 砍掉，只留"系统提示词"单框 |
| **C. 扩展宿主平台** | 开发者/极客 | 扩展面板、安装 Git 扩展、STscript、变量系统 | ⚠️ 不做宿主，做"内置能力" |

**诊断**：A 是产品，B 和 C 让 A 变得不可用。ST 的界面复杂度有 **~70% 服务于 B 和 C**。

### 2.2 架构事实：ST 是一个"本地 Web 应用"，不是 App

```
浏览器前端（201 个 JS，118k 行）
      ↓ 所有请求走 /api/*
Node 服务端（96 个 JS 文件，29k 行，44 个 endpoint）
      ↓
本地文件系统（characters/*.png、chats/*.jsonl、worlds/*.json、settings.json、secrets.json）
```

**关键证据**：
- 生成请求：`public/scripts/openai.js:3148` → `'/api/backends/chat-completions/generate'`
- 后端 endpoint 清单（`SillyTavern/src/endpoints/`）：`characters`、`chats`、`worldinfo`、`settings`、`secrets`、`presets`、`tokenizers`、`search`、`speech`、`stable-diffusion`、`vectors`、`translate`、`caption`、`images`、`sprites`、`themes`、`backups`、`stats`… **共 44 个**。
- 官方唯一"Android 原生"路径 = Termux 里装 Node.js（`SillyTavern-Docs/Installation/Android.md`，需 `pkg install git nodejs-lts nano`，然后 `git clone` + `bash start.sh` + 用 `nano` 编辑 `config.yaml`）。

**对 TeaTalk 的三个硬结论**：

| # | 结论 | 含义 |
|---|---|---|
| 1 | 原生 App 没有 CORS 限制，**可以直连模型厂商 API**，不需要中转服务端 | 删掉 ST 最复杂的一块（服务端代理 + 密钥托管） |
| 2 | 存储从"服务端文件系统"变为"App 沙盒数据库" | 需要重新设计备份/导入导出，且**必须能读 ST 的 `.jsonl` / `.png`**（迁移留存） |
| 3 | 仍有一小部分功能天然需要网络中转（网页搜索、厂商卡片站下载、图片生成代理） | **MVP 不做**，V1 用"可配置代理"预留 |

> ⚠️ **风险提示**：直连厂商 API 会被部分厂商的风控/地域限制拦截；ST 服务端代理存在的一部分原因就是规避这一点。TeaTalk 需要开一个"自定义 Base URL"逃生口（这也是 ST 的 `custom` 源存在的理由）。

### 2.3 ST 的"首屏"长什么样

打开 ST 后用户面对：

| 区域 | 元素 | 数量 |
|---|---|---|
| 顶栏 | 抽屉图标（AI 配置 / API 连接 / 格式化 / 世界书 / 用户设置 / 背景 / 扩展 / 人设 / 角色管理） | **9 个** |
| 聊天区 | 消息流 + 底部输入栏 | 输入栏右侧图标 7 个（停止/续写/代写/发送/STscript 三键） |
| 左下角 | 汉堡菜单 `#options` | **15 项**（关闭聊天、切换面板、作者注、CFG、logprobs、回主页、新检查点、转群聊、新聊天、选聊天、删除消息、重新生成、代写、续写…） |
| 右侧 | 角色列表抽屉 | 含导入、标签、收藏、分组、批量编辑 |

**首屏可点击的顶层入口 ≈ 9 + 15 + 7 = 31 个**（不含消息内动作）。
作为对比，微信聊天页首屏入口 ≈ 4 个。**这就是"不符合现代 App 审美"的量化解释**——不是配色问题，是入口密度问题。

### 3.1 每条消息的 18 个动作（hover 才出现）

| 分组 | 动作 | 数量 |
|---|---|---|
| 常显 | 复制到剪贴板(Ellipsis 入口)、检查点旗标(flag)、编辑(pencil) | 3 |
| **悬停展开** `extraMesButtons` | 翻译、生成图片、朗读(Narrate)、查看 Prompt、从上下文排除、加入上下文、媒体画廊、媒体列表、嵌入文件、Swipe 历史、创建检查点、创建分支、复制 | **13** |

### 3.3 41 个模型接入源（TeaTalk 只该留 5 个）

- **Chat Completion（26）**：OpenAI、Claude、OpenRouter、AI21、MakerSuite/Gemini、VertexAI、Mistral、Custom、Cohere、Perplexity、Groq、ElectronHub、Chutes、NanoGPT、DeepSeek、AIMLAPI、xAI、Pollinations、Moonshot、Fireworks、CometAPI、Azure OpenAI、Z.AI、SiliconFlow、Workers AI、MiniMax
- **Text Completion（15）**：Ooba、Mancer、vLLM、Aphrodite、Tabby、KoboldCpp、TogetherAI、LlamaCpp、Ollama、InfermaticAI、DreamGen、OpenRouter、Featherless、HuggingFace、Generic

**建议保留 5 个 + 1 个逃生口**：

| 保留 | 理由 |
|---|---|
| OpenAI 兼容（`custom`） | 一个入口覆盖 80% 国产模型/中转站 |
| DeepSeek | 国内用户主力，价格敏感 |
| OpenRouter | 一个 Key 通吃多家，极客首选 |
| Anthropic(Claude) | 角色扮演质量口碑 |
| Google Gemini | 免费额度大 |
| **自定义 Base URL** | 逃生口，不解释、不校验、不弹窗 |

> 关键洞察：**Text Completion 源（15 个）在 MVP 全部砍掉**。它们是 2023 年本地推理时代的遗产，普通用户不会自建 llama.cpp；界面里存在这个下拉只会制造"我是不是选错了"的焦虑。

### 3.4 世界书：16 个字段 + 10 个激活设置

| 层 | 内容 |
|---|---|
| 条目字段（16） | 关键词、可选过滤、内容、插入顺序、插入位置、Outlet 名、标题/备注、策略、触发概率、包含组、优先包含、组评分、自动化 ID、角色过滤、触发条件、额外匹配源 |
| 激活设置（10） | 扫描深度、包含角色名、上下文预算%、最小激活数、最大深度、递归扫描、最大递归步数、大小写敏感、全词匹配、溢出报警 |

**普通用户实际需要 3 个**：关键词、内容、插入位置。
其余 13 个字段应放进"高级"折叠区，且**用默认值预填**（这正是 ST 没做好的地方——它把 16 个字段平铺）。

### 3.5 角色卡：11 个字段，但导入格式有 6 种

`index.html` 中角色导入的 `accept`：
```
.json, image/png, .yaml, .yml, .charx, .byaf
```
（世界书导入：`.json, .lorebook, .png`）

| 字段 | MVP 必做 | 说明 |
|---|---|---|
| name / avatar | ✅ | |
| description | ✅ | 角色定义主体 |
| first_mes | ✅ | 开场白 |
| alternate_greetings | ✅ | 多开场白，**用户很在意**，但 UI 容易漏 |
| personality | ✅（可只读展示） | |
| scenario | ✅ | |
| mes_example | ✅ | 少样本示例，对质量影响大 |
| creator_notes | ✅（只读展示） | |
| system_prompt / post_history_instructions | ⚠️ 存但不展示（V1） | 覆盖全局提示词 |
| tags | ✅ | 列表筛选 |
| `extensions` / `character_book` | ⚠️ **存原样不解析（V1 解析）** | 内嵌世界书，很多卡带 |

**结论**：MVP 必须**完整保存整张卡的 JSON**（原样保留未知字段），只渲染认识的字段。这是"不丢数据"的最低成本做法。

## 4. 功能全景表（按域，含处置）

图例：复杂度 = 低/中/高；依赖 = `纯前端` / `需Key` / `需后端`；处置 = ✅MVP / 🔶V1 / 🔷V2 / ⬜预留架构位 / ❌砍掉

### 4.1 对话与会话

| 功能 | 一句话价值 | 复杂度 | 依赖 | 处置 | 理由 |
|---|---|---|---|---|---|
| 单角色聊天（流式） | 产品的核心循环 | 中 | 需Key | ✅ | 不做就没有产品 |
| 重新生成 | 不满意就重roll | 低 | 需Key | ✅ | 最高频动作之一 |
| **多版本切换（swipe）** | 同一轮保留多个候选回复 | 中 | 纯前端 | ✅ | ST 的招牌体验，数据上是"消息 N 个版本" |
| 编辑消息 | 改我说的/改它说的 | 低 | 纯前端 | ✅ | 高频 |
| 删除/清空 | 基础 | 低 | 纯前端 | ✅ | |
| 继续生成（Continue） | 说一半断了 | 低 | 需Key | 🔶 | V1，长回复场景 |
| 会话列表/重命名/搜索 | 找到旧聊天 | 低 | 纯前端 | ✅（搜索 🔶） | 列表必须，搜索 V1 |
| 消息内 Markdown 渲染 | 代码块/粗斜体/引用 | 中 | 纯前端 | ✅ | 不做则观感极差 |
| **分支（Branch）** | 从某条消息开出新时间线 | 高 | 纯前端 | 🔷 | **但数据模型必须现在留 `parentId`** |
| 检查点（Checkpoint） | 给对话拍快照 | 中 | 纯前端 | 🔷 | 与分支同源，数据位共享 |
| 群聊（Group Chat） | 多角色同场 | 高 | 需Key | 🔷 | 复杂度炸弹（发言顺序/上下文预算） |
| 作者注（Author's Note） | 在深度 N 插入临时指令 | 中 | 纯前端 | 🔷 | 进阶，但"深度插入"能力要预留 |
| 消息朗读/翻译 | 无障碍 + 非母语 | 中 | 需Key | 🔶（TTS） | V1 |
| 消息表情/贴纸 | 情绪表达 | 低 | 纯前端 | ❌ | 非 ST 核心，且需内容生态 |

### 4.2 角色与人设

| 功能 | 价值 | 复杂度 | 依赖 | 处置 | 理由 |
|---|---|---|---|---|---|
| 角色卡导入（PNG/JSON/CHARX） | 新用户的第一个动作 | 中 | 纯前端 | ✅ | **P0，必须零文档可用** |

## 5. 核心旅程：ST 现状 vs TeaTalk 目标

> 点击数为**估算**（基于 §2.3 的首屏结构与各面板字段数），用于比较量级，不作为精确验收指标。

### 5.1 旅程 A：首次使用 → 配模型 → 能发第一条消息

| 步 | ST 现状（桌面） | ST 现状（移动端） | TeaTalk 目标 |
|---|---|---|---|
| 1 | 浏览器打开 localhost:8000（或先装 Termux 跑 `bash start.sh`） | **几乎不可行**：需 Termux + node + git | 打开 App |
| 2 | 若未配人设 → 弹 onboarding（提示"ST 面向高级用户"，**必须填人设名**） | 同左，键盘遮挡 | 直接进引导 |
| 3 | 从 9 个顶栏图标中认出"插头"= API Connections | 图标无文字，靠猜 | 引导页："先选一个大模型" |
| 4 | 选 API 类型（下拉 **26 选 1**） | 原生 select，滚动很长 | 卡片式 **5 选 1** |
| 5 | 填 API Key | 同左 | 粘贴 Key（带格式校验提示） |
| 6 | 点 Connect → 拉模型列表 → 选模型（下拉可能 100+ 项） | 同左 | 自动拉取 + 搜索 + 推荐默认 |
| 7 | （可选）调 temperature 等 105 个滑块 | 小屏滑块难操作 | 3 个滑块，带人话解释 |
| 8 | 关闭面板 → 打开右侧角色抽屉 → 选角色 → Start Chat | 抽屉叠加抽屉 | 直接进角色列表 |
| **合计** | **约 12–20 次交互 + 1 次"装服务端"** | **实际上劝退** | **4 步**：选服务商 → 粘 Key → 选模型 → 完成 |

**痛点排序**：① 装服务端（P0，直接劝退手机用户）→ ② 26 选 1 的选择过载 → ③ 图标语义不明 → ④ 设置项密度。

### 5.2 旅程 B：导入角色卡 → 开始对话

| 步 | ST 现状 | TeaTalk 目标 |
|---|---|---|
| 1 | 右抽屉 → Characters | 角色页 → 右上 "+" 或空态大按钮 |
| 2 | 点导入（或拖拽文件） | 系统文件选择器（按扩展名过滤） |
| 3 | 弹出"导入角色"对话框（逐张确认/标签/头像） | **直接导入，无对话框**；成功后 toast + 卡片飞入 |
| 4 | 列表刷新 → 找到刚导入的卡（可能被排序埋没） | 自动滚动到新卡并高亮 |
| 5 | 点角色 → 右侧详情 → 选 "Start chat" | **点卡片 = 直接开聊**（详情在卡片右上角"⋯"里） |
| 6 | —— | 首次开聊若未配模型 → 就地弹"配模型"引导（不打断用户的地图） |
| **合计** | **约 7–9 次 + 1 个阻断式对话框** | **3 次** |

**移动端额外痛点**：
- `accept=".json, image/png, .yaml, .yml, .charx, .byaf"` 依赖浏览器 file input，Android 上部分文件管理器会把这些扩展名过滤掉 → **用户"看不到我的卡"**。
- 建议：MVP 支持系统分享（Share Intent）接收卡文件 + "从聊天记录/下载目录导入"。

### 5.3 旅程 C：世界书（三痛点里最被低估的一个）

| 步 | ST 现状 | TeaTalk 目标 |
|---|---|---|
| 1 | 顶栏"书"图标 → World Info 面板 | 角色详情 →「世界书」标签页 |
| 2 | 顶部下拉选择世界书（"全局/角色/聊天"三种作用域混在一个下拉） | **不做全局作用域**：世界书属于角色 |
| 3 | 从条目列表点"新建" | "+ 新建条目" |
| 4 | 面对 **16 个字段**，其中 13 个不懂 | **只显示 3 个**：关键词、内容、什么时候插入 |
| 5 | 保存 | 保存（自动保存更好） |
| 6 | **回到上一级，找到"全局世界"勾选框，勾上才生效** ← 最大坑 | 不存在这一步（天然绑定） |
| **合计** | **约 10–12 次 + 概念负担** | **4 次** |

> **关键设计判断**：ST 的"世界书是全局资源，需要手动激活"是它架构的历史包袱（多世界书合并）。TeaTalk 应改为 **"世界书是角色的附属资产"**，一对多，自动生效。这个改动在数据模型上几乎零成本，在用户心智上收益巨大。

### 5.4 旅程 D：回溯（不满意 → 重来）

| 步 | ST 现状 | TeaTalk 目标 |
|---|---|---|
| 1 | 鼠标划过消息 → 出现 13 个图标 | 长按消息 |
| 2 | 点左/右箭头切换 swipe | ActionSheet：重新生成 / ◀ 2/4 ▶ / 编辑 / 复制 / 更多 |
| 3 | 或点旗标创建检查点、点分支图标创建分支 | 更多 → 从这里新建分支 |
| **合计** | 依赖 hover，移动端需 2 层 | 1 次长按 |

## 6. 冗余的四个来源（诊断）

| # | 来源 | 具体表现 | 量化 | 处置原则 |
|---|---|---|---|---|
| 1 | **三套重叠的设置入口** | AI 配置 / User Settings / Formatting 三个面板都能改"上下文、格式、显示" | 556 input 中约 1/3 是"同一件事的三种入口" | **单一信息架构**：一个设置页，按"聊天/模型/外观/数据"分区 |
| 2 | **历史功能的考古层** | Text Completion 15 源、CFG、Instruct、logprobs、Tokenizer、Horde、NovelAI、Kobold —— 全是 2023 本地推理时代的遗产 | 41 接入源里约 35 个对 2026 新用户零价值 | **不兼容历史**，只服务当前主流 |
| 3 | **平台化冲动** | 扩展面板、从 Git 安装扩展、STscript、变量系统、主题市场 | 44 个扩展 / 297 命令 / 157 宏 | **不做宿主**，把 20% 高频能力内置 |
| 4 | **桌面交互假设** | hover、右键、tooltip、拖拽、横向滚动、多列布局 | 108 个 popup / 13 个悬停图标 / 快捷键 | **移动优先重设计**，见 §7 |

**一句话**：ST 的冗余不是"加了太多功能"，而是**"没有做过减法决策"**——每个功能都被保留，因为它的用户群是愿意读文档的极客。

## 7. 10 个移动端重设计点

> 每条含：ST 现状 → 问题 → TeaTalk 方案 → 验收标准

### ① 导航骨架：9 个顶栏抽屉 → 3 个底部 Tab + 页面栈

- **ST**：`#top-settings-holder` 里 9 个图标（AI 配置、API、格式化、世界书、用户设置、背景、扩展、人设、角色），点击展开 13 个宽抽屉，抽屉还能叠抽屉。
- **问题**：手机上抽屉占满屏、返回键行为不可预期、图标无语义。
- **方案**：底部 3 Tab —— **聊天 / 角色 / 我的**。会话页、角色详情、世界书、模型配置都用**标准页面栈**（push/pop），系统返回键 = 返回上一页。
- **验收**：任意页面按返回键 ≤ 3 次回到首页；无任何"抽屉套抽屉"。

### ② 消息操作：18 个 hover 图标 → 长按 ActionSheet

- **ST**：1 常显 + 13 悬停 + 编辑态 7 + 推理 5。
- **问题**：hover 在手机上不存在；ST 折叠后用户仍要进二级菜单。
- **方案**：**长按消息 → 底部 ActionSheet 一级 5 项**（重新生成 / 切换版本 / 编辑 / 复制 / 更多）；"更多"里放删除、从这里分支、朗读、查看本次 Prompt。**双击消息 = 编辑**（快捷方式）。
- **验收**：单条消息的常用操作 ≤ 2 次触达；一级菜单项 ≤ 5。

### ③ 会话内菜单：15 项汉堡 → 分组 Sheet

- **ST**：`#options` 15 项（含 CFG、logprobs、转群聊、检查点等）。
- **方案**：会话页右上"⋯" → Sheet 分 4 组：**会话**（重命名/清空/导出）、**角色**（看设定/换世界书/换背景）、**生成**（重新生成/续写/代写）、**高级**（查看 Prompt/模型参数）。CFG、logprobs、群聊转换**不出现**。
- **验收**：Sheet 每组 ≤ 4 项；"高级"组对普通用户默认折叠。

### ④ 设置：556 input / 132 select → 三层层级 + 搜索

- **ST**：所有设置平铺在抽屉 + inline-drawer 的二维迷宫里，28 个折叠区块。
- **方案**：
  - **L1 常用（8 项内）**：字体大小、深色模式、流式开关、上下文长度、回复长度、temperature、自动保存、显示时间戳。
  - **L2 高级（折叠）**：其余参数，按"模型/上下文/显示/数据"分组。
  - **L3 搜索**：设置页顶部搜索框（ST 有 `setting-search.js` 但入口隐蔽）。
- **验收**：新用户 30 秒内找到"字体大小"；全部设置项 ≤ 40 项（ST 约 400+）。

### ⑤ 宽面板：双列 1280px 布局 → 全屏页 + BottomSheet

- **ST**：PC 端左右抽屉 + 中央聊天三列；`mobile-styles.css` 只是在 `max-width:1000px` 时把 flex-basis 改 100%，本质是"缩小的桌面"。
- **方案**：**全屏页面**用于有导航语义的内容（角色列表、世界书列表、设置）；**BottomSheet**（可拖拽高度）用于上下文操作（选模型、换背景、消息动作）。参考 QQ/微信的"页面 + 半屏浮层"节奏。
- **验收**：无横向滚动；无 `<select>` 原生下拉（改用底部选择器）。

### ⑥ 弹窗：108 个 popup class → 统一 3 种组件

- **ST**：108 处 popup，`<dialog>` 只用 1 次，其余手写 div + 各自定位/层级/关闭逻辑。
- **方案**：只允许 3 种：**Dialog**（确认/危险操作）、**BottomSheet**（选择/操作）、**Toast/Snackbar**（反馈）。禁止第四个。
- **验收**：代码中不存在自定义定位的浮层；所有弹窗有统一进出动效与遮罩。

### ⑦ 手势与返回：定义白名单，不与系统冲突

- **ST**：`hotkeys.md` 明确 **"Hotkeys are disabled for mobile devices"**；移动端手势只有"生成中滑动停止"（`Gestures: Enable swipe gestures for generation (Mobile only)`）。
- **方案**（白名单，共 5 个）：

| 手势 | 行为 |
|---|---|
| 左边缘右滑 / 系统返回 | 返回上一页 |
| 聊天页左右滑（消息区） | 切换上一条/下一条 swipe 版本（仅当该消息有多版本时） |
| 长按消息 | ActionSheet |
| 双击消息 | 编辑 |
| 下拉（会话列表顶部） | 刷新/搜索 |

- **禁区**：不做"滑动删除会话"（易误触，且无撤销），改用长按菜单。不做"摇一摇"。
- **验收**：任何手势都有非手势的等价入口（可发现性）。

### ⑧ 输入区：桌面 textarea → 移动输入栏

- **ST**：`#send_form` 左右各一组图标（左：汉堡；右：停止/续写/代写/发送 + STscript 三键），桌面回车发送。
- **方案**：**单行自适应输入框**（最多 5 行）+ 左"+"（附件/图片/世界书引用）+ 右**发送/停止二合一按钮**（生成中变停止）。回车 = 换行（移动端约定），发送靠按钮。键盘弹起时消息列表自动上推，发送后**保持键盘**（连聊体验）。
- **验收**：输入栏高度 ≤ 56dp（单行）；生成中按钮明确变"停止"；键盘遮挡 0 次。

### ⑨ 调试信息：hover 悬浮 → 不进主流程

- **ST**：logprobs 面板、token 概率、`Token Probabilities` 悬浮窗、Prompt Inspector。
- **方案**：MVP **完全不展示**。V1 提供"高级 → 查看本次发送内容"只读页 + 输入栏右侧 token 计数小字。
- **验收**：主界面无任何 token/概率/延迟数字（可放"关于/诊断"页）。

### ⑩ 命令与宏：297 命令 / 157 宏 → 隐藏 + 渐进披露

- **ST**：斜杠命令和宏是"文档能力"，界面上零可发现性。
- **方案**：MVP 只支持 `/help` 与 `/clear`（不做命令面板）。V1：输入 `/` 唤起**带描述的搜索面板**（只暴露 10–15 个高频命令）。宏：MVP 不支持用户编辑，只做**内置 6 个变量**的自动替换（`{{char}}`、`{{user}}`、`{{time}}`、`{{date}}`、`{{persona}}`、`{{char_personality}}`）。
- **验收**：普通用户无需知道"宏"这个词也能正常使用。

## 10. 首屏信息架构建议

### 10.1 结构

```
App 启动
├── 有历史会话 → 直接进「聊天」Tab（上次会话）
└── 无历史 → 引导流（3 屏）
     ├── 屏1：选择大模型（5 张卡片 + "我有自定义地址"）→ 粘 Key → 测试连接
     ├── 屏2：导入第一张角色卡（"从文件导入" / "先给我一个示例角色"）
     └── 屏3：介绍 3 个核心动作（聊/换版本/加世界书）→ 进聊天

底部 3 Tab
├── 聊天
│   ├── 会话列表：角色头像 + 名字 + 最后一句摘要 + 时间 + 未读点
│   ├── 长按 → 重命名 / 导出 / 删除（带撤销）
│   └── 右上 ✓/搜索
├── 角色
│   ├── 网格（3 列）+ 顶部搜索 + 收藏筛选
│   ├── "+" → 导入（文件 / 分享进入）
│   └── 点卡片 → 开聊；卡片"⋯" → 详情 / 编辑 / 世界书 / 导出
└── 我的
    ├── 模型（当前模型 + 切换 + 参数）
    ├── 人设（头像 + 名字 + 描述）
    ├── 世界书（我的世界书列表）
    ├── 外观（深色模式 / 字体大小 / 背景）
    ├── 数据（备份 / 恢复 / 导出 / 清理）
    └── 关于 / 反馈
```

### 10.2 首屏入口数对比

| | ST | TeaTalk 目标 |
|---|---:|---:|
| 首屏顶层可点入口 | 31（9 图标 + 15 菜单 + 7 输入栏） | **6**（3 Tab + 1 主按钮 + 2 列表内操作） |
| 到达"开始聊天"的步骤 | 12–20 + 装服务端 | **4** |
| 设置项总数 | ~400+ | **≤ 40** |
| 需要认识的专有名词 | > 30（instruct / CFG / logprobs / lorebook / character book / quick reply…） | **≤ 8** |

### 10.3 视觉基调（对齐"像手机 QQ/微信"）

- **信息密度**：单列列表、左头像右文字、时间在右上或分组标题。
- **气泡**：角色消息左对齐（无气泡或浅底），用户消息右对齐（品牌色底）。**不要**做成微信"完全对称气泡"——角色扮演长文本用满宽更易读。
- **导航**：底部 Tab + 顶部大标题（Large Title），无侧滑抽屉。
- **色彩**：1 个品牌色 + 中性灰阶 + 跟随系统深色；不做"主题商店"。
- **动效**：仅 3 种 —— 列表进出、Sheet 升降、消息出现。无多余装饰。

## 11. 功能陷阱清单（"看起来必要，实际会拖垮 MVP"）

| # | 陷阱 | 为什么危险 | 正确做法 |
|---|---|---|---|
| 1 | **"导入即用"幻觉** | PNG 角色卡是 base64 塞进 PNG 的 tEXt chunk，还有 CHARX(zip)、YAML、byaf 变体；字段命名有 v1/v2/v3 三代 | 先做"读取 + 原样存"，解析失败时降级为"只取名字和头像" |
| 2 | **世界书"做全套"** | 16 字段 + 10 激活设置的完整实现要 2 周，且用户看不懂 | 只做关键词 + 内容 + 3 档位置；字段存全但 UI 藏 |
| 3 | **分支/检查点** | 一旦做了分支树，编辑器、撤销、删除语义全部翻倍 | MVP 只做"同一条消息的多个版本"，分支字段留空 |
| 4 | **Prompt 拼装** | 角色卡有 `system_prompt`/`post_history_instructions` 覆盖，还有世界书注入、作者注、深度插入…顺序错了输出就崩 | 定义一条**固定拼装管线**（system → 世界书 → 历史 → 作者注@深度 → 用户输入），不开放顺序编辑 |
| 5 | **群聊** | 说话顺序、上下文预算分配、@ 指定，是三个独立难题 | V1 再说，但现在 `chat` 表就要有 `participants` 概念位 |
| 6 | **流式 + 撤回 + 多版本并发** | 用户在生成中切版本/编辑/删除，状态机容易炸 | 明确状态机（idle/generating/stopping），生成中禁用会改上下文的消息操作 |
| 7 | **"原生 App 不需要服务端"的过度自信** | 网页搜索、厂商卡片下载、部分厂商风控，都可能需要中转 | 预留"代理 Base URL"配置；MVP 不实现，但要能配置 |
| 8 | **迁移** | 老用户有几十张卡和几年聊天记录，搬不过来就流失 | MVP 必须支持：ST 的 `characters/*.png`、`chats/*.jsonl`、`worlds/*.json` 三件套导入 |
| 9 | **密钥安全** | 明文存 preferences 是常见事故 | Android Keystore 加密；备份时排除密钥 |
| 10 | **"再加一个功能吧"** | ST 就是这样长成 118k 行的 | §8 判定规则 + MVP 清单**锁死**，新需求一律进 V1 Backlog |

## 12. 预留架构位（现在不做，但数据模型必须留）

| 预留项 | 字段/接口形态 | 现在就要的成本 | 不预留的后果 |
|---|---|---|---|
| 分支 | `message.parent_id`、`message.branch_id`、`chat.root_message_id` | 加 3 个可空字段 | V1 要重刷全部历史数据 |
| 消息多版本 | `message.version_group_id` + `version_index` | 2 个字段 | 同上 |
| 宏/变量 | `render_context`（变量表）+ 渲染管线单一入口 `render(text, ctx)` | 1 个函数抽象 | 到处散落字符串替换 |
| 正则/输出清洗 | 渲染管线里的 `hooks: List<Renderer>` | 1 个接口 | 后期插不进 |
| 群聊 | `chat.participants: List<CharacterId>`、`message.speaker_id` | 2 个字段 | 会话表结构重造 |
| 媒体 | `message.media: List<MediaRef>`（图片/语音/立绘） | 1 个 Json 字段 | 消息表迁移 |
| 多连接配置 | `connection_profile` 独立表（provider/baseUrl/model/params） | 1 张表 | 用户要反复重配 |
| 卡片原始数据 | `character.raw_json: String` | 1 个字段 | 未知字段丢失，无法回写 |
| 世界书全字段 | 16 字段全入库 | 建表时一次到位 | 后期加列 + 补数据 |
| 元数据 | `created_at`、`updated_at`、`source`（import/manual）、`app_version` | 常规 | 无法做同步/迁移/排错 |
| 国际化 | 所有 UI 字符串走资源文件 | 习惯问题，零成本 | 后期全量替换字符串 |

> **这一节是本文最有"架构杠杆"的部分**：预留成本 ≈ 2 人日，不预留的返工成本 ≈ 15–20 人日。

## 13. 风险与待确认

| # | 风险/待确认 | 影响 | 建议 |
|---|---|---|---|
| 1 | 直连厂商 API 的**风控/地域限制**（尤其 OpenAI/Anthropic） | 部分用户"配了也用不了" | 默认推荐 DeepSeek/OpenRouter/国内中转；错误信息给"换 Base URL"指引 |

| 6 | 与 01/02 号调研的**重叠判断**（技术选型、竞品） | 结论可能冲突 | 以本文的功能取舍为准；技术实现以 01/02 为准 |
